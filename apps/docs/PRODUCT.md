# Product

## Register

brand

## Platform

web

## Users

The primary audience is a TypeScript developer building a product that works with CGM data. They need reliable calculations and useful output without inheriting someone else's dashboard or application model.

Designers, researchers, creative directors, and technical leads are a secondary audience. They may not install the package themselves, but they need to see that GlucoseIQ can support a thoughtful product before they recommend it to a team.

Teams moving from `diabetic-utils` are also supported. Migration matters, but it should not define the first impression.

## Product Purpose

GlucoseIQ analyzes CGM readings and returns typed metrics, chart-ready data, and optional SVG. Product teams own credentials, storage, workflows, and interface design.

The documentation site states that boundary on the homepage. A visitor can inspect real package output, find the code behind it, and reach the quickstart without reading a sales pitch.

## Positioning

GlucoseIQ handles CGM normalization, analytics, and render-ready output. The product team controls the application around it.

## Conversion & Proof

- The primary action is **Read the quickstart**.
- The fallback is **Browse the API**. GitHub remains available in the main navigation and closing section.
- The shortest useful description is: **CGM readings become typed metrics, chart-ready data, or SVG.**
- The homepage proof is a borderless AGP signal produced from fixed synthetic readings and the typed report returned from the same data.
- Before acting, a visitor should see that the output comes from the published API, understand where GlucoseIQ stops, and find the package that fits their application.
- Proof comes from the generated homepage report, cited implementation references, package tests, and the source. There are no testimonials or customer logos to claim.

## Brand Personality

The writing is precise and assured. The visual design respects the subject without imitating a hospital portal or a consumer wellness app.

The page should feel made by people who care about data, type, and interaction. Visitors should find the documentation without hunting for it.

## Anti-references

Avoid the familiar generated landing-page look: centered gradient headlines, walls of identical cards, fake terminals, glass panels, tiny uppercase labels, and decorative product metrics disconnected from the library.

Do not imitate an awards portfolio, a brokerage dashboard, or a patient-facing health app. Keep content visible without scroll-triggered effects. Use working output instead of inflated claims.

## Design Principles

1. **Show the library working.** The strongest proof is a report produced by GlucoseIQ.
2. **Keep the product boundary visible.** Visitors should know which responsibilities remain in their application.
3. **Treat glucose data with care.** Label units, preserve safety language, and never let decoration imply a medical conclusion.
4. **Make technical depth easy to enter.** Lead to the quickstart, then let API detail unfold when the reader asks for it.
5. **Give every sentence a job.** Copy should explain behavior, remove doubt, or help someone move.

## Accessibility & Inclusion

Target WCAG 2.2 AA. Content must remain visible without motion, keyboard focus must be obvious, interactive targets must be at least 44 pixels tall, and status must never rely on color alone. Support reduced motion, high contrast, narrow screens, and text zoom. Charts need concise text alternatives, units, and labels.
